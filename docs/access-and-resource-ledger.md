# External access, resources and license-resolution ledger

Created during approved Completion Step 06, 2026-10-24. This is a **planning and evidence ledger**, not a permission grant, account check, purchase, legal opinion or deployment record. No credential values were read or recorded, no source/model terms or account checks were performed, and no access entitlement was inferred from the proposal. After the initial exact-wheel exception, the user authorized bounded tooling/dependency-metadata acquisition and read-only GitHub verification within a 150 MB ceiling. That approval excludes hosted CI execution, source/model acquisition, account checks and deployment. Tool acquisition uses the approved network scope; subsequent verification uses local inputs with offline controls.

An item is **verified locally** only when a local receipt/test establishes the stated fact. **Recorded historically** means a previous acquisition/report contains evidence, without a current online recheck. **Unverified** means the required fact is unknown. **Blocked** identifies a deliverable that cannot proceed until the stated approval, access or evidence exists. Preparing a config/manifest does not verify access to the service it describes.

The accountable role in each row owns obtaining the resolution, even when another administrator must grant access. The **project owner (user)** remains accountable until a named human accepts a specialist role. Target steps are dependency gates, not invented calendar deadlines. No message to an external administrator/provider is authorized by this ledger.

## Dependency and license inventory overview

The inventory separates **declared**, **locked**, and **installed** dependencies. Declared dependencies express supported requirements in `pyproject.toml`; the lock resolves concrete versions/artifact hashes; installed metadata describes this one environment. These sets need not be identical. Optional extras being declared does not show they are installed, and a local install does not prove another platform can resolve them.

## Closure evidence and sensitive information

For each resolved row, retain the date, responsible human/role, exact service/artifact/purpose, source of evidence, allowed scope, expiry/recheck trigger, approval reference and result. Use a redacted receipt or secret reference for access checks. Account numbers, tenant identifiers, keys, tokens, passwords and raw credential stores do not belong here. A provider's key existing somewhere on a machine is not authorization to inspect or use it.

Local deterministic tests and the prepared CI checks use fictional inputs and offline execution; no live provider, licensed private dataset or model download is needed for those checks. CI separates dependency acquisition during bootstrap from the subsequent network-isolated check stage. Local configuration checks are not a hosted execution result. The proposal's external integrations still require actual separately authorized deployments and executions to close their deliverables. Preparation can make those steps reviewable without falsely marking them complete.

## 5W1H recap

- **What:** an accountable list of access, compute, budget and rights prerequisites.
- **Why:** surface blockers before experiments or integrations depend on them.
- **When:** resolve each row before its named step; recheck when purpose, artifact/version, terms or entitlement changes.
- **Where:** this nonsecret ledger links to local evidence and future approved redacted receipts.
- **Who:** the named resolution role is accountable; the project owner holds that responsibility until a human accepts it.
- **How:** obtain bounded approval, check the exact current requirement, preserve evidence, verify the real outcome and keep unknowns explicitly open.
